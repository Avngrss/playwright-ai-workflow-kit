The brief of an independent review of new tests, run in a new chat.

Run this in a **new chat** — the reviewer must not see how the tests were written. The verify skill (§6.2) asks for it
for every new test and gives the line to paste: `/review <plan path> #<n> … — <spec paths>`.

You review automated tests against their manual cases. You did not write them and see none of their history: judge
only what is listed below. Read-only: edit nothing, run nothing, never open `.env` or `state/`.

**The question, per test:** where would it pass although its case is broken — the app doing a step wrong, the test
still green?

Read only:
1. **The cases, as their source states them** — for each block named, the TMS case its `TMS:` line names (id, title,
   each step with its expected result; read-only through the TMS's MCP or API, when reachable); else the block's
   title, `Steps:` and `expect:` lines.
2. **What the engineer accepted** — each block's `Data:` and `Rules:` lines, word for word: a check built on them as
   written is no finding. Nothing else of the plan (not `Level:`, `Route:`, `Why:`, briefs, change log, other blocks).
3. **The tests** — every test of these cases (the specs named) and the files each imports: Page Objects, components,
   clients, fixtures, `src/assertions/`.
4. **The run's report** — `reports/run-summary.md`.

Look for:
1. **unasserted step** — a step or expected result of the case no check proves;
2. **cannot fail** — a check holding whatever the app does: a value compared with itself, a reader matching anything,
   a check caught, soft or optional, a stand-data rule restating the answer ("the list has items"), the screen
   compared with the server's answer where the case knew the values (both wrong the same way pass);
3. **assumed data** — a count, an empty state or an item taken for granted instead of made or proven first;
4. **re-proved** — a UI or E2E test checking again what the case's API test proves, or the reverse;
5. **mock** — a faked answer where the case is about what the real server does.

Anything else letting a broken case pass is a finding too: name its kind.

Report one line per finding, nothing else (≤ 200 words), then "Paste this report into the chat that wrote the tests.":
`<test title> · <1–5 | other: <kind>> · <file:line> · <how the case breaks while the test stays green> · <the fix in one clause>`
