# Setup

One app or ten — the same layout, and adding an app changes nothing of another, no rename, no move
(`00-project-map.md` §Apps). Rules: `00-project-map.md` (layout, apps, `.env` names), `02-guardrails.md`
(secrets, never retry a refused sign-in), `01-workflow.md` (asking); roles and sessions inside specs: `specs.md`.
**The agent adapts, the user does not.** Ask only what you cannot find out, do the rest, and say plainly what you
found, did and still miss.

`/setup` — What: **app** → §2 · **sign-in** → §3 · **another account or role** → §3.9; any other map edit → §5.
Nothing said → a map with no app of its own yet → §2; otherwise ask which of the three.

## 1. Safety — always

- Secrets and `env:prepare`: `02-guardrails.md` §Secrets and settings. A URL, a public client id and scopes are not
  secrets — save them from chat. The map's rows and block lines first, then `env:prepare`: it edits `.env` and
  `.env.example` in place (a value in its own line, a new name next to its app's group); only `npm run env:prepare
  -- --tidy` lays both out by app again.
- **The user may choose the chat** for the test account (offered, never the default): save the values to `.env` at
  once through `env:prepare`, never repeat them, and say once: "Saved to .env. These values are now in this
  session's history — fine for a test account on a test environment; for anything else, change the password." The
  same for a secret pasted unasked. Client secrets only ever in `.env`.
- Test accounts only — never someone's personal account. Never type a login or password into the MCP browser;
  sign-ins run through the universal code (§3.7).
- **Every wrong password counts toward the account's lockout** — the tests' tries and the user's own. A test types a
  password only when it is known to work on **that** sign-in service: the user signed in with exactly those values
  by hand (a private window), or the tests already have. After a refusal — a new password included — nothing runs
  until the user says the manual sign-in with the values now in `.env` worked. Never delete `state/*.failed.json` to
  try an unchecked password.

### 3.3 Explore signed out — facts, not guesses

With the Playwright MCP — none in this agent → the saved-session script, signed out — as `live-app.md` says.
**Look, never submit:** no form gets made-up data — it loads the stand's sign-in service and its limits and shows
nothing the real sign-in won't. What is invisible signed out (the password step's button) gets the likeliest label,
corrected from the first real sign-in's message (§3.7).

1. Open the URL. Where does it land — the app (public), its own sign-in page, an external identity provider (OIDC:
   `<host>/.well-known/openid-configuration` — its token endpoint and allowed grants), an SSO page? **No answer**
   (timeout, DNS, certificate) → stop: "`<url>` did not respond (<what happened>). Check the address, the VPN, or
   whether this environment is up. Nothing was saved yet." Never guess another address. **JSON instead of a page**
   (or no web UI) → an API-only app: `ui: none`; credentials per §3.5 without the browser rows. **The app for a
   visitor, with a sign-in link** (a shop, a portal) → find signed out a page that sends a visitor to sign in (the
   account or profile page from the menu) → `members only: ${<its UI env name>}/<its path>` (names, never a value);
   the sign-in smoke checks there, since the home page looks the same signed in and out.
2. The form's **visible** steps: fields, buttons (email → Next → password is common), SSO-only buttons. A frontend
   repo at hand → its auth setup **in source code** (an OIDC client, a sign-in request — never its `.env`): where
   the signed-in app keeps its token.
3. **API base and Swagger** (not given) — after the first successful sign-in (§3.7 step 3): load the saved session
   into the MCP browser, read the hosts of its data requests (`browser_network_requests`; the script:
   `page.on("request")`), save the API row (`<APP>_API_URL`, or `API_BASE_URL` for the first app) through
   `env:prepare`. Then find the contract **without guessing**, each once, in this order: (1) a Swagger UI page on
   the API host → the definition's address from the page itself (its `swagger-initializer.js`, `configUrl`, the
   `url` / `urls` it loads); (2) otherwise the common paths `/swagger.json`, `/swagger/v1/swagger.json`,
   `/openapi.json`, `/v3/api-docs`, `/api-docs`, `/swagger`, `/swagger/index.html`; (3) the definition answers 401
   → one more request with the test account's headers (through the auth code; the token is never shown). Judge a
   hit by **content**, never the status: JSON with an `openapi` / `swagger` key, or a page with `swagger-ui`. A
   hit → the Docs column of the app's API row (`{<API env name>}/<path>`), not `.env`; its answer types by `npm run
   api:types -- <app>` once the app's first client is written (the implement skill), and again whenever the API
   changes. Nothing → stop looking; report it as **Missing** (§3.4). It blocks only API tests.

### 3.5 API credentials — facts first, one trial at most

Decided once; the block keeps it. Only a confidential client needs a secret — most web apps need nothing beyond the
test account.

**Facts first** — none asks anything, none uses the account: the provider's discovery document (`token_endpoint`,
`grant_types_supported`); the app's own `…/authorize?client_id=…&scope=…` request seen signed out; the contract's
`securitySchemes`; after the first sign-in, the **names** (never values) in `state/<app>.<role>.<host>.session.json`
— a token entry, and whether a refresh token is there.

**Then the first that fits:**

| # | When the facts say | `api:` | Needs from the user | API tests then depend on |
|---|---|---|---|---|
| 1 | the contract: an API key or Basic | `key` / `basic` | the key in `.env` / nothing | nothing else |
| 2 | the provider allows `password` | `token` — password grant with the app's own client id and scopes, no secret | nothing | the identity provider only — no browser |
| 3 | 2 refused, the session keeps a refresh token | `refresh-token` | nothing | one browser sign-in, then new tokens over HTTP |
| 4 | the app has its own sign-in request that answers a token | `login-request` with `session from: json <field>` | nothing | that request only — no browser |
| 5 | the signed-in app keeps a token | `session-token` — no field in `session token:` when the entry holds the token itself | nothing | the UI sign-in (once per run, cached) |
| 6 | cookies only | `login-request` if the app has its own sign-in request, else `session-cookies` | nothing | that request / the UI sign-in |
| 7 | the team gives a test client | `token` with its secret, or `client_credentials` (no user — no per-role tests) | client id (chat is fine), secret (`.env`, by the user) | the identity provider only |
| 8 | none fits | `custom` (§3.6) | — | — |

**The one trial (row 2)** — after "ready", write the block with the app's client id and run once: `npx playwright
test --project=smoke:<app> --no-deps -g "data requests"`. Passed → keep it. `unauthorized_client` /
`unsupported_grant_type` → this client may not sign in this way; nothing is paused — go to rows 3–5; never guess
another client id. `invalid_grant` → wrong login or password; the account pauses as in §3.7.

A question only for a real choice — e.g. row 2 works **and** the team offers a test client: "Where should API tests
get their credentials? 1. Keep <the source that works> (recommended) — <its dependency> · 2. Use the team's test
client — no browser; you enter the secret in .env". The report names the source and what would remove a dependency.

**`.env` names:** one account `<APP>_LOGIN`, `<APP>_PASSWORD`; with roles `<APP>_<ROLE>_LOGIN`,
`<APP>_<ROLE>_PASSWORD`; `<APP>_CLIENT_ID` set from what you saw; `<APP>_API_KEY` / `<APP>_CLIENT_SECRET` filled by

### 3.6 When neither universal client fits

Neither a form nor a token endpoint (a signed request, a client certificate, a custom SSO handshake), or sign-in code
the user points at → write or port `src/setup/auth/project.ts` with `browserSession(browser, role, platform)` and

### 3.7 Verify — not done until this passes

1. `npm run auth:check` — ✓ for the account (every role, when there are roles).
2. The sign-in smoke is the template's `tests/smoke/sign-in.smoke.spec.ts` — skipped until the block exists, **never
   edited or replaced**. Everything app-specific comes from the block: `signed in when:` (it must tell the app from a
   sign-in page on the same host — e.g. `url starts with ${UI_BASE_URL}/app`, or a `text "…"` only the app shows)
   and `session check:` (a cheap "who am I" API request found in the signed-in app's requests and confirmed in the
   contract). It checks the first account only, on purpose.
3. Run it, this app only: `npx playwright test --project=smoke:<app>`. No API base yet → the UI test first (`-g "web
   app"`), then §3.3 step 3, then the whole file. With roles, `npm run auth:sign-in -- <app> all` signs each one in
   the same way. A public app (`ui: none` + `api: none`) has one test, "The web app opens": its address answers and
   its page shows. **Green = at least one test passed** — a run of skips only is not a smoke: the block or the app's
   rows are wrong.

A failure is reported, not retried — the code never repeats a refused sign-in with the same login and password.
Turn its message into this shape:

> **API sign-in check failed**
> - Request: `GET /api/users/me` as the test account
> - Status: **401 Unauthorized**, reason: `invalid_token: audience mismatch`
> - Needed: the token is issued for a different API — ask the team for the right scope or audience.
> - UI tests are not affected.

| The run says | Tell the user |
|---|---|
| `needs X, Y in .env` | which entries are still empty |
| `did not get signed in … showing "…"` | what the page shows: a form with an error → check the login and password in .env; a code, captcha or SSO page → a blocker (§3.4) |
| `Login step … found nothing to click … buttons "…"` | a step label in the block is wrong: fix it from the listed buttons, run once more — not a refusal, nothing paused |
| `invalid_client` | wrong client id or secret |
| `unauthorized_client` / `unsupported_grant_type` | this client may not get tokens this way — the team decides |
| `invalid_grant` | wrong login or password, or the account is locked |
| `invalid_scope` | a scope this client may not ask for |
| 401 with a reason | the server's reason (`WWW-Authenticate`) and what it implies |
| 403 | signed in, but the user lacks rights — a permissions question |

**A wrong password, in this order:** `npm run auth:check` first (it names, without showing, a value `.env` reads cut
short — a `#` outside quotes); then the user signs in **once** by hand in a private window with the same values.
Fails by hand too → the password is wrong for this service: ask for the right one or a reset; a locked account → the
team unlocks it — never "try again". Works by hand → only then delete that account's `state/*.failed.json` and run
once more. A new password in `.env` gets one attempt on its own. Never loop.

   - Passed → §3.3 step 3 (its API and Swagger), then the whole smoke (§3.7).
   - Refused (the page says the account has no access, or `invalid_grant` / 403) → nothing more is tried. The block
     gets its own account lines (`login: ${BETA_LOGIN}`, `password: ${BETA_PASSWORD}`; with `api: token` also the
     `token field: username` / `password` lines), entries prepared empty; the report's first line: "**Sign in to

## 4. The ```auth block and its API modes

One block per app in §Auth, starting `platform: <app>` (a block without it serves a one-app map only), read by
`src/setup/auth/auth-config.ts`; `.env` **names** (`${NAME}`), never values; no block = login not set up. What the
template then guarantees: `data-and-fixtures.md` §Sign-in setup.

```auth
platform: shop
ui: form
start: ${UI_BASE_URL}
step: fill "Email" with login
step: click "Next"
step: fill password with password
step: click "Log in"
signed in when: url starts with ${UI_BASE_URL}
login: ${SHOP_LOGIN}
password: ${SHOP_PASSWORD}

api: session-token
session token: localStorage oidc.user:* access_token
session check: ${API_BASE_URL}/me
```

- **Steps**, as a person does them: `fill "<field>" with login|password` (label, placeholder or accessible name) ·
  `fill password with password` · `click "<button>"` · `wait for "<text>"`. **Signed in when:** `url starts with
  <url>` or `text "<visible text>"`.
- **`api:` modes**: `token` (token url + `token field:` lines; a public client's password grant needs no secret; no
  browser) · `refresh-token` (one browser sign-in, then tokens over HTTP) · `session-token` (the signed-in app keeps a
  bearer token, `session token: <storage> <key> [<field>]` — no field: the entry's value is the token; API tests
  depend on the UI login, once per run) · `session-cookies` · `login-request` (the app's own sign-in request, no
  browser; `login url:`, `login body:`, `login format:`, `session from:` `cookie` — the default — or `json <field>`, a
  token in the answer) · `key` (`key header:`, `key:`) ·
  `basic` · `custom` (`project.ts`, §3.6) · `none`. `ui: none` + `api: none` = a public app.
- **Optional**: `session check: <url>` (a cheap "who am I") · `session max age: <minutes>` · `members only: <url>` (an
  app open to visitors: a page that sends a visitor to sign in — the sign-in smoke opens it, §3.3 step 1) · `tenants:
  GET <path> → <id>, <name>` (`00-project-map.md` §Apps — how the app lists an account's tenants, the two being
  fields of each entry, `<list>[].id, <list>[].name` when the list is a field of the answer; written when a stand
  search first needs it; the header of `scripts/agent/stand-find.mjs`).
- **Roles**: no `roles:` line = one test account (role `user`); a further account adds its own `login <role>:` /
  `password <role>:` lines (§3.9); the first account's lines never change. Whether signing out ends every session of
  the account is recorded as a comment here by the app's first sign-out test (the check: `specs.md`).
- **Apps on one identity provider**: the further app's block says `sign-in like: <app>` and writes only what differs
  — e.g. `platform: beta` · `sign-in like: alpha` · `start: ${BETA_UI_URL}/app` · `signed in when: url starts with
  ${BETA_UI_URL}/app` · `token field: client_id = <beta's own client id, when it has one>`, and its own `login:` /
  `password:` when the shared account is not let in. `qa:gate` fails a missing borrowed block or a circle.

## 6. Starter conversion

Turning a project back into the reusable kit — asked in words, no command of its own. Inventory and classify
every file — **keep** (rules, skills, commands, reusable docs, package and config files such as
`playwright.config.ts`, `tsconfig.json`, `.gitignore` and a generic `.env.example`, generic scripts and workflow
templates, the shared sign-in smoke, `agents/mcp.json` with safe MCP only) · **remove** (tests, plans,
`src/<kind>/<app>/` folders, the product's map rows and blocks, known-bug rows, `src/**` code bound to the
product even in a generic folder, sample tests not marked as templates, visual snapshot folders, product-only
docs and URLs, committed credentials or sessions, app-specific CI) · **generated** (`state/`, `reports/allure/**`, `reports/run-summary.*`,
`test-results/`, `playwright-report/`, `.playwright-mcp/`, scratch scripts and dumps, traces, videos, logs, a
local `.env` — delete or ignore) · **unsure** (ask, never delete); `.github/**` per file. Nothing is deleted
before the user decides on the lists; then `npm run test:list` and `npm run qa:gate`. The map, known-bugs and
`docs/test-strategy.md` become blank templates, `src/data/sweeps.ts` an empty list. Report Removed · Preserved
· Unsure · Verification · Remaining risks; not complete while unsure files remain unless the user accepted it.
